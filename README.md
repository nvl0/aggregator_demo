# Демонстрационная версия работы агрегатора трафика

Сервис раз в 60 секунд разбирает netflow-файлы (flow) по директориям nas_ip,
сопоставляет трафик с активными сессиями из Postgres и сохраняет посчитанные
чанки трафика обратно в базу.

## Быстрый старт

Зависимости: `docker`, `docker compose`.

```
make docker-up   # поднять весь стек: postgres + миграции + сервис
make db-up       # поднять только postgres и накатить миграции
make jaeger-up   # поднять jaeger для локального трейсинга (см. «Наблюдаемость»)
make test        # все тесты (юнит + storage + postgres, нужен docker)
make build       # собрать бинарник в bin/
```

`Makefile` — обёртка над скриптами `src/scripts/*.sh`; полный список
таргетов — `make help`. Прямой запуск скриптов (`run_test_all.sh`,
`run_test_pg_repository.sh`, `run_test_storage_repository.sh`,
`run_test_usecase.sh`, `start_docker.sh`) остаётся рабочим, если Makefile
почему-то не подходит.

## Конфигурация

`conf.yaml` (путь — `CONF_PATH`) задаёт базовые значения, часть из них
переопределяется переменными окружения:

| conf.yaml            | env               | дефолт                          |
|-----------------------|-------------------|----------------------------------|
| `postgres.url`         | `PG_URL`          | —                                |
| `postgres.db_name`     | `PG_DBNAME`       | `aggregator`                     |
| `postgres.timezone`    | `PG_TIMEZONE`     | `Asia/Tashkent`                  |
| `postgres.password`    | `PG_PASSWORD`     | значение из `conf.yaml`          |
| `worker_pool.size`     | `WORKER_POOL_SIZE`| `10`                             |

Переменные без ключа в `conf.yaml`:

| env                 | назначение                                              | дефолт            |
|----------------------|----------------------------------------------------------|--------------------|
| `CONF_PATH`          | путь к `conf.yaml`                                        | —                  |
| `FLOW_DIR`           | путь к flow-директории                                     | —                  |
| `SUBNET_DISABLED_DIR`| путь к директории с диском исключённых из подсчёта подсетей| —                  |
| `DEBUG`              | `true` включает debug-уровень логов                        | `false`            |
| `METRICS_ADDR`       | адрес служебного http (`/metrics`, `/healthz`, `/readyz`)  | `:2112`            |
| `TRACING_ENDPOINT`   | адрес otlp-коллектора трейсов (host:port)                  | пусто — выключено |
| `VERSION`            | версия сборки, попадает в логи и `aggregator_build_info`   | `dev`              |
| `MEASURE`            | `enable` включает лог длительности именованных замеров     | выключено          |
| `FLOWGEN`            | `true` включает синтетическую генерацию flow при старте (dev)| выключено        |

## Как работает агрегатор

Сервис запускается 1 раз в 60 секунд. Если предыдущий цикл не был закончен,
новый цикл не начнётся до тех пор, пока старый не завершится.

1. Считывание flow-директории — список nas_ip директорий, нужен для путей
   агрегации и фильтрации сессий.

   ```
   ├ nas_ip
   ├── tmp
   │   ├── ft-filename
   ├── ft-filename
   └── tmp-filename

   filename - название файла netflow;
   nas_ip - имя директории ip nas сервера;
   nas_ip/ft-filename - собранный flow за n-минут, который не был агрегирован;
   nas_ip/tmp-filename - текущая трансляция flow, которая не должна быть агрегирована пока не превратится в ft-*;
   tmp/ft-filename - собранный flow за n-минут, который был агрегирован;
   ```

2. Получение сессий из базы данных.
3. Запускается цикл, nas_ip директории обрабатываются пулом воркеров
   ограниченного размера (см. «Масштабируемость»).
4. Считывание flow: вход в директорию, создание `tmp`, перенос готовых
   netflow-файлов (см. пример дерева) в `tmp`.
5. Агрегация netflow по направлениям: внешняя сеть, внутренняя сеть. Netflow —
   файл с информацией о количестве и размере пакетов между ip-адресами
   (`ByteSize`, `SrcAddr`, `DstAddr`). Агрегация — простое сложение байтов;
   получатель или отправитель должен принадлежать внутренней сети. При
   инициализации нулевой трафик создаётся по всем разрешённым направлениям.
6. Просеивание трафика сопоставляет ip-адреса агрегированного трафика из flow
   с текущими активными сессиями из базы: сессия должна быть активной (шаг 2),
   её `nas_ip` должен совпадать с `nas_ip` директории flow — иначе трафик не
   запишется. Результат — чанк, смесь данных активной сессии и агрегированного
   трафика.
7. Запись чанков в базу данных.
8. Удаление подсчитанных flow.

## Отказоустойчивость и идемпотентность

Между коммитом чанков в бд и удалением обработанного flow нет и не может быть
общей транзакции: одна сторона — Postgres, другая — файловая система. Падение
процесса или ошибка удаления в этом окне привели бы к тому, что на следующем
цикле те же flow-файлы читались бы повторно и трафик задваивался.

Имена уже закоммиченных flow-файлов хранятся в таблице-чекпоинте `flow_batch`
(`nas_ip, file_name`, первичный ключ по обоим полям). Порядок работы одного
`nas_ip`:

1. Загрузка имён закоммиченных файлов по `nas_ip`.
2. `repository.Flow.StreamFlow` построчно читает файлы из `tmp/`, пропуская
   уже закоммиченные (`skipFileNames`), без склейки файлов в память — каждая
   строка сразу передаётся в `FlowAccumulator.AccumulateLine`. Метод
   возвращает полный список имён файлов в `tmp/` (включая пропущенные).
3. Если новых файлов нет — это повтор после сбоя: подсчёт пропускается,
   выполняется только очистка `tmp/` (при условии, что в директории `nas_ip`
   есть хотя бы один файл; если файлов нет вовсе, очистка откладывается до
   цикла, в котором для этого `nas_ip` появится хотя бы один файл).
4. Чанки и полный список имён файлов пишутся **в одной транзакции**.
5. Чекпоинт удаляется только после успешного удаления файлов. Если удалить
   файлы не удалось, записи `flow_batch` остаются — именно они не дадут
   посчитать этот трафик второй раз.

Паника при обработке одного `nas_ip` перехватывается внутри
`src/tools/workerpool`: остальные воркеры продолжают работу, слот пула
освобождается, cron-цикл не падает. Восстановленное значение и стек
логируются через колбэк `workerpool.WithOnPanic`, который задаёт
`AggregatorUsecase` — сам пакет пула о логгере приложения не знает.

## Наблюдаемость

Служебный http на `METRICS_ADDR` (дефолт `:2112`):

- `GET /metrics` — метрики Prometheus (`aggregator_cycle_*`, `aggregator_nas_*`,
  `aggregator_chunks_saved_total`, `aggregator_accounted_traffic_bytes_total`,
  плюс стандартные `go_*`/`process_*` и `go_sql_*` для соединений с бд).
- `GET /healthz` — liveness.
- `GET /readyz` — readiness (проверяет соединение с Postgres).

Пример правил алертинга Prometheus на этих метриках — `docs/monitoring/alerts.yml`.

Метрика `aggregator_nas_phase_duration_seconds{phase=...}` раньше имела два
значения лейбла `phase` для этапа разбора flow — `prepare_flow` и
`parse_flow`. После перехода на потоковое чтение (`StreamFlow` +
`FlowAccumulator`) они схлопнуты в одно значение `stream_flow`. Если у вас
настроены дашборды или alert-правила по старым значениям — их нужно
поправить.

Структурные логи — JSON через `log/slog` в stdout, уровень переключается
`DEBUG=true`.

Трейсинг — OpenTelemetry, экспорт по OTLP/HTTP в `TRACING_ENDPOINT` (по
умолчанию выключен). Спан `aggregator.cycle` на весь цикл, дочерний
`aggregator.nas` на обработку каждого `nas_ip`. Локально: `make jaeger-up`
поднимает Jaeger (UI — `localhost:16686`, OTLP/HTTP — `:4318`); `docker-up`
уже прокидывает в сервис `TRACING_ENDPOINT=jaeger:4318`.

## Масштабируемость

Агрегация nas_ip директорий выполняется пулом воркеров ограниченного размера
(`src/tools/workerpool`) вместо неограниченного запуска горутины на каждую
директорию. Диспетчер блокируется на занятом пуле — это создаёт бэкпрешер, и
число одновременных транзакций, открытых файлов и горутин перестаёт зависеть
от количества nas_ip директорий. Размер пула — `worker_pool.size`
(см. «Конфигурация»).

Лимит одновременно открытых соединений с Postgres равен `worker_pool.size + 2`
(две дополнительные — под параллельные стартовые запросы мапки каналов и мапки
онлайн сессий).

### Замеры

Замер выполняется dev-инструментом `src/cmd/loadgen` на реальном Postgres и
диске, не в CI:

```
./run_loadgen.sh -cleanup            # удалить прошлую синтетическую нагрузку
./run_loadgen.sh -n 200              # создать 200 nas_ip директорий и сессий
./run_loadgen.sh -pool-size 10 -run  # один цикл агрегации с замером времени
```

## Разработка

```
make lint         # golangci-lint (докер, версия как в CI)
make test-unit    # юнит-тесты usecase/tools/config (без docker)
make test-storage # тесты файлового репозитория
make test-pg      # интеграционные тесты postgres-репозитория (поднимает db-up)
make mocks        # регенерация моков
```

CI (`.github/workflows/ci.yml`): lint, тесты (с реальным Postgres),
`govulncheck`, сборка docker-образа. Обновления зависимостей — через
Dependabot (`.github/dependabot.yml`, еженедельно).
