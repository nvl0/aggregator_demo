# Демонстрационная версия работы агрегатора трафика
### Зависимости
docker, docker compose

### Инструкции
```
Тесты: /src/scripts/run_test_*.sh, где * - all, pg_repository, storage_repository, usecase 
Старт сервиса: /src/scripts/start_docker.sh
```

## Схема работы агрегатора
Сервис запускается 1 раз в 60 секунд. Если предыдущий цикл не был закончен, 
то новый цикл не начнется до тех пор, пока старый цикл не завершится.

1. Считывание flow-директории. Мы получаем список nas_ip директории. Они нужны для указания путей для агрегации и фильтрации сессий.

```
Древо директории flow должно выглядеть следующим образом, где:
├ nas_ip
├── tmp
│   ├── ft-filename
├── ft-filename
└── tmp-filename

filename - название файла netflow;
nas_ip - имя директории ip nas сервера;
nas_ip/ft-filename - собранный flow за n-минут, который не был агрегирован;
nas_ip/tmp-filename - текущая трансляция flow, которая не должна быть агрегирована пока не превратится в ft-*;
tmp/ft-filename - собранный flow за n-минут, который был агрегирован;
```

2. Получение сессий из базы данных.

3. Запускается цикл, nas_ip директории обрабатываются пулом воркеров ограниченного размера (см. раздел «Масштабируемость»).

4. Считывание flow происходит путем: входа в директорию, создание директории tmp, переноса готовых netflow (см. пример древа) 
файлов в директорию tmp.

5. Агрегация netflow по направлениям: внешняя сеть, внутренняя сеть. Netflow представляет из себя файл, в котором содержится информация по количеству и размеру пакетов
между ip-адресами. ByteSize, SrcAddr, DstAddr - размер переданных байтов, получатель, отправитель. Агрегация осуществляется простым сложением
количества байтов. Получатель или отправитель должен принадлежать внутренней сети. При инициализации нулевой трафик будет создан по всем
разрешенным направлениям, который в последствии будет агрегирован.

6. Просеивание трафика нужно для сопоставления ip-адресов агрегированного трафика из flow и текущих активных сессий из базы данных.
Критерии для просеиваниия следующие, чтобы трафик посчитался: сессия должна быть активной (получена из пункта 2), nas_ip сессии должен 
совпадать с nas_ip директорией flow. В противном случае трафик не будет записан. Результатом просеивания является чанк - смесь данных из актвиной сессии
и агрегированного трафика.

7. Запись чанков в базу данных.

8. Удаление подсчитанных flow. 

## Масштабируемость

Агрегация nas_ip директорий выполняется пулом воркеров ограниченного размера
(`src/tools/workerpool`) вместо неограниченного запуска горутины на каждую
директорию. Диспетчер блокируется на занятом пуле — это создает бэкпрешер, и
число одновременных транзакций, открытых файлов и горутин перестает зависеть
от количества nas_ip директорий.

Настройка:

```
conf.yaml: worker_pool.size (по умолчанию 10)
env:       WORKER_POOL_SIZE переопределяет значение конфига
```

Лимит одновременно открытых соединений с Postgres равен `worker_pool.size + 2`
(две дополнительные — под параллельные стартовые запросы мапки каналов и мапки
онлайн сессий).

### Замеры

Замер выполняется dev-инструментом `src/cmd/loadgen` на реальном Postgres и
диске, не в CI:

```
./run_loadgen.sh -cleanup            # удалить прошлую синтетическую нагрузку
./run_loadgen.sh -n 200              # создать 200 nas_ip директорий и сессий
./run_loadgen.sh -pool-size 10 -run  # один цикл агрегации с замером времени
```

## Идемпотентность и отказоустойчивость

Между коммитом чанков в бд и удалением обработанного flow нет и не может быть общей
транзакции: одна сторона — Postgres, другая — файловая система. Раньше падение
процесса или ошибка удаления в этом окне приводили к тому, что на следующем цикле
те же flow-файлы читались повторно и трафик задваивался.

Теперь имена уже закоммиченных flow-файлов хранятся в таблице-чекпоинте `flow_batch`:

```
flow_batch (nas_ip, file_name), первичный ключ (nas_ip, file_name)
```

Порядок работы одного `nas_ip`:

1. Загрузка имён закоммиченных файлов по `nas_ip`.
2. `ReadFlow` конкатенирует только те файлы из `tmp/`, которых нет в чекпоинте,
   и возвращает полный список имён файлов, лежащих в `tmp/`.
3. Если новых файлов нет — это повтор после сбоя: подсчёт пропускается, выполняется
   только очистка `tmp/` (при условии, что в директории `nas_ip` есть хотя бы один
   файл; если файлов нет вовсе, очистка откладывается до цикла, в котором для этого
   `nas_ip` появится хотя бы один файл).
4. Чанки и полный список имён файлов пишутся **в одной транзакции**.
5. Чекпоинт удаляется только после успешного удаления файлов. Если удалить файлы
   не удалось, записи `flow_batch` остаются — именно они не дадут посчитать
   этот трафик второй раз.

Проверено вручную на реальном Postgres и диске (5 синтетических `nas_ip`,
`run_loadgen.sh`): временно отключалась очистка `tmp/`, после чего один цикл дал
`chunk_count = 5` и `batch_count = 5` при файлах, оставшихся в `tmp/`. Повторный
цикл без новых файлов не изменил `chunk_count` (осталось 5) — дублирования не
произошло. После добавления ещё 5 `nas_ip` и повторного цикла `chunk_count` вырос
ровно на 5 (стал 10) — столько же, на сколько он вырос на первом прогоне: новые
файлы посчитаны один раз, старые не пересчитаны. После возврата очистки `tmp/`
следующий цикл дал `batch_count = 0` — чекпоинт удалён вместе с обработанным flow.

Паника при обработке одного `nas_ip` перехватывается внутри `src/tools/workerpool`:
остальные воркеры продолжают работу, слот пула освобождается, cron-цикл не падает.
Восстановленное значение и стек логируются через колбэк `workerpool.WithOnPanic`,
который задаёт `AggregatorUsecase` — сам пакет пула о логгере приложения не знает.
